# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

cgkit is a Go CLI toolkit for computational genomics research. It provides commands for sequence analysis, NGS data wrangling, and bioinformatics operations, with particular focus on Oxford Nanopore (long-read) sequence processing. The underlying library (sequence I/O, alignment, SAM/BAM/CRAM handling) lives in the separate `cghts` module (`github.com/compgenlab/cghts`).

**Module:** `github.com/compgenlab/cgkit`
**Go version:** 1.24.9
**CLI framework:** Cobra
**Library dependency:** `github.com/compgenlab/cghts`

## Commands

```bash
# Build all targets (darwin_arm64, darwin_amd64, linux_arm64, linux_amd64, windows_amd64)

# Run all tests

# equivalent to:
GOCACHE=/tmp/go-build-cache go test ./...

# Run with CPU profiling
```

## Dependency on cghts

All format I/O and algorithms come from `github.com/compgenlab/cghts` (packages
`seqio`, `align`, `htsio` and its subpackages, `support/*`, `analysis/seq`).

How the `cghts` dependency resolves, by context:
- **Local builds** use the `go.work` workspace (parent dir, untracked) that joins
  a sibling `cghts` checkout, so you build against your live local `cghts` tree. The
  `Makefile` deliberately does **not** set `GOWORK=off`.
- **Remote/CI builds** (no `go.work` present) use the **latest released cghts from
  GitHub**: the GitHub Actions workflow runs `go get github.com/compgenlab/cghts@latest`
  before vet/test/build, with `GOPRIVATE=github.com/compgenlab/*` so a freshly
  pushed cghts tag is fetched directly from GitHub (no module-proxy/sumdb lag).
- The committed `go.mod` pin is the fallback for `go install` users and the
  source archive; keep it current with `make bump-cghts`.

### Cutting a release
The cghts tag must land on GitHub before cgkit builds against it:
1. **cghts**: tag `vX.Y.Z` on `main`, push the tag.
2. **cgkit**: `make bump-cghts` (pins `go.mod` to the new cghts), commit
   `go.mod`/`go.sum`, push. CI's `go get cghts@latest` then resolves the same tag.

## Architecture

This repo holds only the CLI layer: `main.go` (entry point with `--profile`
support) and `internal/cmd/` (Cobra commands). The only third-party dependencies
are cobra/pflag; everything genomics-related, including the Parquet genotype
store, is delegated to `cghts`.

There are now no exceptions to "CLI layer only". The genotype store lives in
`cghts/varstore` — the schema, both backends, and the `Calls(Query)` query API —
so `vcf-toparquet` and `vcf-varquery` are thin wrappers over it: flag parsing,
output formatting, and nothing else. What stays here is presentation: `tsvColumns`,
`minDPOf`/`vouchedMinDP`, and the TSV/JSON/VCF writers. When adding to the store,
add it upstream and `make bump-cghts`; a change that needs a CLI flag *and* store
support is two commits in two repos, in that order.

### Remote inputs

Inputs may be local paths, `http(s)://` URLs or `s3://` objects; **outputs are
always local**. Dispatch is cghts's `iosource`, and index sidecars resolve over
the same transport as the data, so an indexed region query still seeks.

- The `s3://` blank import lives in **`internal/locator`**, a leaf package, not in
  `main.go`. `main` is not linked into `go test ./internal/...`, so a test
  asserting the "no transport registered (registered: s3)" message would pass
  there while the shipped binary said otherwise; keeping it in a package the
  tests link makes the test the guard on the import. This is why cgkit carries
  the AWS SDK: measured **26.5 MB → 38.4 MB** for linux_amd64 (+11.9 MB, +45%).
  `-ldflags "-s -w"` brings that back to 26.8 MB — not enabled, since stripping
  is an orthogonal decision, but the option is there if size matters.
- `internal/locator.IsRemote` wraps `iosource.IsRemote` rather than
  reimplementing it. cgkit must classify a locator exactly as the library will
  dispatch it; a classifier that disagreed by one edge case (a Windows drive
  letter is not a scheme) would not fail loudly, it would open the wrong thing.
- **`targets.go` classifies scheme-first, then `os.Stat`.** A URL cannot be
  stat'd, and a stat-first rule would demote it to an inline selector, which
  parses as a contig name and matches nothing — an empty result rather than an
  error. Only values containing `://` past the first character change meaning,
  and nothing in the selector grammar can look like that, so a mistyped locus
  still gets a locus error and `HLA-A*01:01:01:01` is untouched. Both pinned by
  tests; this is the single riskiest change in the remote work.
- **Outputs are refused by name**, via `locator.CheckLocalOutput`, always *after*
  a command's stdout branch or `-` breaks. There is no writer-side equivalent of
  a byte source, and a multipart upload is not a shape a BAM or Parquet writer
  can stream into, so this is a real boundary rather than an unfinished one.
- Costs stated rather than hidden: a *streaming* read of a remote object
  transfers the whole thing (no index to skip with), and `vcf-gtcount --threads N`
  fetches the index N times because a tabix reader is not concurrency-safe.
- Deliberately **not** covered: FASTA/FASTQ/BED streaming inputs, `vcf-concat`'s
  chunked reader, `vcf-annotate` sources, remote writes, `gs://`.

### CLI Command Structure

Commands are registered in `internal/cmd/root.go` and grouped by file format or domain:
- `fasta-cat`, `fasta-wrap`, `fasta-gc` — FASTA operations
- `fastq-gc` — FASTQ operations
- `sam-stats` — Summary statistics for SAM/BAM/CRAM: read counts, mapping rates, Q30, depth, SAM flag breakdown, per-reference counts, optional `--tags` value distributions and `--calc-insert` median. Profiles the first read of each pair only (ports `ngsutils bam-stats`). Phase 1 omits the `--gtf` gene-model and `--bed` on-target stats.
- `seq-pairwise`, `seq-revcomp` — Sequence analysis
- `ont-polya` — Per-read poly(A)/cleavage site calling from a strand-specific aligned BAM. Finds the mRNA 3' end (FLAG 0x10, or `--antisense`), traces back through the tail with a windowed A-fraction test, and reports the first tail base's 1-based genomic position. The trace deliberately continues past the soft-clip boundary into aligned bases, since aligners absorb genome-encoded A's at real sites — which also makes the tool prone to reporting internal priming; `polya_source` (`--polya-src`) is the partial hook for filtering that downstream. Secondary/supplementary alignments are skipped. PAS motif annotation is deliberately out of scope: it is a per-site property needing a reference, so it belongs after clustering reads into sites.
- `ont-tags` — ONT adapter/primer detection and trimming from FASTQ, with alignment statistics (embeds a default primer set; override with `--primers-fasta`)
- `ont-umi-cluster` — Collapse similar UMIs in a coordinate-sorted BAM into `MI` groups
- `ont-umi-dedup` — UMI deduplication: selects one representative per MI group from coordinate-sorted BAM. Secondary/supplementary alignments are dropped (cannot be reliably resolved in coordinate order). Supports `--threads` for parallel BGZF compression.
- `ont-umi-lookup` — Match reads in an aligned BAM to UMI clusters from `ont-umi-cluster` output
- **gVCF support**: `vcf-varquery` reads reference blocks as the coverage they are — one reference row per block per sample (never one per base), `alt` `.`, `min_dp` the block's own `MIN_DP`, `dp` `.` since a block measures no single base, `gq` from `RGQ`. A position no variant record mentions is answerable when a block covers it; a **gap** between blocks is not, because nothing was reported there. `Gate.Admits` prefers `MinDP` over `DP`, which is load-bearing rather than tidy: `Missing` passes every gate by design, so a block-derived call would otherwise be admitted unconditionally. **`vcf-toparquet` refuses a gVCF** — it used to produce a store with `<NON_REF>` in the sites catalog, `AC`/`AN` counting a block allele, and every block reduced to its first base, all silently. The refusal keys on **a reference block record** (`rec.IsRefBlock()`), not on the header: a joint-genotyped cohort VCF — a DRAGEN msVCF, a GATK `GenotypeGVCFs` callset — keeps the `##ALT=<ID=NON_REF>` line inherited from its source gVCFs while containing no blocks, and `##ALT=<ID=*>` declares the ordinary spanning-deletion allele, so `isGvcfHeader` rejected exactly the input this command is for. VCF 4.5 makes that unfixable at the header level: the gVCF unspecified allele and the spanning-deletion allele are the same ALT ID. `vcf-strip` still must decide from the header (it writes its header before reading a record); `vcf-toparquet` need not, since a failed conversion `Discard()`s. A mixed `G,<NON_REF>` record is a variant record and converts, with the block allele masked out of the catalog, the calls and AC the way any non-focal alternate is (`-v` counts them). Conversion is deferred to the next cgkit release and is a **cohort** operation -- the unit is a *set* of gVCFs merged together, since one gVCF is single-sample and a one-sample store answers nothing that querying the gVCF directly does not. See `PLAN.md` §2.
- `vcf-strip` — Remove annotations (FILTER/INFO/FORMAT/samples/ID) from a VCF. **Refuses to drop `INFO/END` from a gVCF** unless `--force-end`, because a reference block's extent lives entirely in that field: removing it leaves a file that still parses while claiming one base of coverage where it claimed thousands. Detection is from the header (`##ALT=<ID=NON_REF>` or `<*>`, a `##GVCFBlock` line, a declared `MIN_DP`/`LEN`) because the output header is written before the first record is read, so a record-level answer arrives too late to keep the `##INFO` declaration; if detection misses and a block carrying `END` turns up anyway, it fails rather than emit records with an undeclared `END`. `--all --keep-info END` was always an escape hatch; `--force-end` is the inverse.
- `vcf-tobed` — Export variant positions as BED. The interval is the **reference extent** the record covers (`rec.RefSpan()`), not the alternate position: `AltPositions` resolves an SV's *partner breakpoint*, which may be on another chromosome, and using it as an extent gave a plain deletion one base too many and collapsed a multi-base-ALT deletion to a single base. Reference blocks are skipped -- they describe coverage, not variants -- and a mixed `G,<NON_REF>` record keeps its real allele. This **diverges from ngsutilsj deliberately**, which ends a deletion at `POS+len(REF)`; the parity goldens still pass only because `testdata/sample.vcf` has no multi-base-REF deletion.
- `vcf-gtcount` — Genotype (GT) distribution per site across samples, for sites given inline or via `--sites`. Answers a different question from `vcf-varquery` (a per-site *summary*, not per-sample genotypes) and looks each site up by random access, so it needs a tabix-indexed input and **refuses** a region, whole contig or BED interval — there is no single position to look up. Shares `vcf-varquery`'s target grammar and parser.
- `vcf-toparquet` — Convert one or more VCFs into a sparse Parquet genotype store (several inputs is how whole-genome callsets ship: one per chromosome). Inputs must carry **exactly the same samples**; differing column order is **remapped**, because genotype columns are positional and getting that wrong silently attributes every genotype to the wrong person. A set mismatch errors, naming what differs. Inputs must not overlap (no revisiting a chromosome, no going backwards within one) since that would duplicate sites and split AC/AN; supplying them in coordinate order is not required for correctness but keeps pruning tight (~1.8x on a locus query). A failed conversion calls `Writer.Discard()` so no partial store is left to look valid or block the retry through the overwrite guard — including the "no DP field" refusal, which used to run *after* `Writer.Close()` and so left all three members on disk, whereupon the overwrite guard blocked the very `--no-callable` retry its error message asks for.: `BASE.calls.parquet` (one row per ALT-carrying genotype), `BASE.sites.parquet` (one row per interrogated site, carrying **AC/AN** allele counts alongside `n_carriers`/`n_called`/`n_lowdp` sample counts — these are not interchangeable: a 1/1 genotype is one carrier but two alt alleles, so AC ≥ n_carriers whenever a homozygote is present, and AN counts alleles ungated while n_called counts samples passing `--min-dp`. AC/AN are recomputed from the store's own samples rather than copied from source INFO, which would be wrong after splitting multiallelics or converting a cohort subset, and they are computed outside the `--no-callable` guard since allele counts are a property of genotypes, not coverage), `BASE.regions.parquet` (contiguous runs of covered sites per sample). **A store is a directory** — `cohort/{calls,sites,regions}.parquet` plus `manifest.json.gz` — and a trailing `/` on `--out` is optional and meaningless. The former filename-prefix form is gone; keeping both meant every path decision first had to guess which was meant, and `TrimStoreSuffix` had to consult the filesystem, which cannot work for a remote locator. `vcf-varquery` accepts the directory, either spelling, or any member path; `varstore.TrimStoreSuffix` owns that and no longer touches the filesystem. **The manifest is what makes a store readable rather than merely present**: written last by `Writer.Finish`, required at open, with each member's recorded row count checked against that member's own parquet footer — the only thing that catches a well-formed member belonging to a *different* conversion. It carries a per-chromosome census accumulated by the writer *as it writes*, so it records rows rather than intent; that matters because `cgkit.source` and `cgkit.contigs` are stamped before the first record is read, so a store covering 3 of 22 chromosomes still names all 22 inputs and declares all 22 contigs. There is **no escape hatch**: an unfinished store answers "not assayed" for everything it never reached, which is indistinguishable from the honest answer for a position the source never reported. Stores from before manifests must be re-converted; `vcf-varsummary` is how you find out why one was refused. Conversion **refuses to overwrite an existing store** — any one of the three members already present under `--out`, or a prefix-form base naming an existing directory, stops it and asks for `--force`; writing truncates all three, and a half-replaced set is worse than either whole outcome. The guard keys on the members, so an existing directory holding unrelated files is fine and its contents are left alone. The sites file is **not** derivable from the calls: taking distinct loci out of the calls only recovers every site when the store holds an entire joint callset, and over a sample subset the sites nobody in that subset carries vanish silently, so a later query reports "never interrogated" for a position that was in fact observed and reference. Records are normalized to one variant per row (multiallelics split, focal allele recoded to 1, other alternates masked to `.` so a `1/2` sample is correctly a carrier of both; AD taken per allele, not summed). Indels are **not** left-aligned. A site counts as called only when the caller actually made a call there *and* DP ≥ `--min-dp` — `./.` at high depth is a declined call, not a covered one. **The regions file records runs of *catalog sites* at which a sample was called; the interval form is a compression of that per-site fact and claims nothing about the bases in between.** A plain VCF reports variants and asserts nothing about any other position, so the sites catalog is the exact boundary of what is answerable: an off-catalog locus is `not_assayed` for every sample, never a set of reference calls, even where run intervals bracket it (`Classify` returns early on the catalog check for precisely this reason, and `vcf-varquery` warns). Stores record `cgkit.span_semantics` = `sites`; only a gVCF-derived store (`blocks`, not yet produced) could answer off-catalog. See the GVCF memory. `-v/--verbose` reports progress **as a `chrom:pos` coordinate** rather than a record count alone — counts advance at the rate variants are called, so on a sparse input a quiet stretch is indistinguishable from a stall, whereas a position can be checked against the contig length. The chromosome-transition line carries it too, since the periodic tick only fires every 100,000 records and a smaller contig would otherwise name itself and go silent. Plus a per-chromosome trace and a conversion summary, all on stderr — notably a census of which of DP/GQ/AD the input actually carries, since a gate can only act on a field the data has.
- `vcf-varsummary` — Describe a store or a VCF without querying genotypes: samples, contigs, provenance, per-chromosome census. **The default report never reads a record** — O(header) on both backends, so it is instant against a 200 GB VCF — and `--samples`/`--counts`/`--sites` are the opt-in passes. That is a hard guarantee with a test to match (a fixture whose header is valid and whose records are not, so anything reading past the header fails). A store's facts come from its manifest; a VCF has none, because it is not a conversion, and the report says so rather than fabricating a `--min-dp` or a creation date. For an *indexed* VCF the contigs that carry records come from the tabix index for free — the cheapest useful thing a VCF summary can report; exact record counts are not recoverable from an index and are not estimated from one. `--format json` emits a store's manifest verbatim, which is the promise that makes gzipping it acceptable. It must also work on a store that cannot be *opened* for querying, since with no escape hatch for a missing manifest this is the only way to learn why one was refused.
- `vcf-varquery` — Query genotypes over either a VCF or a `vcf-toparquet` store, chosen by path or `--store`. **Two independent axes**: `--variant` selects sites, `--sample` selects subjects, and they compose — naming both asks what those subjects' genotypes are at those sites, which used to be a hard error ("separate modes"). An axis left unnamed is unrestricted, not empty. `--variant` is the **only** site selector (there is no `--region`) and takes `chr1`, `chr1:1000-2000`, `chr1:1000`, `chr1:1000:A:T`, or a **file** — VCF/BCF, BED, or whitespace-separated `chrom pos [ref alt]` — detected from content, with BED and site lists told apart by whether column 3 is numeric (a BED end always is, a REF allele never is). A value is a file when one exists by that name, so a mistyped locus still gets a locus error. An exact locus additionally requires non-numeric REF/ALT, which is what lets contig names carry colons (`HLA-A*01:01:01:01` splits into four fields too, but its tail is numeric); anything matching no shape is a contig name taken whole, and a target that matched nothing is reported so a malformed locus does not read as a real negative. BED is 0-based half-open where site lists and VCF are 1-based, so a misdetection would shift coordinates rather than fail — hence `-v` names the format read and a file yielding no targets is an error. `vcf-gtcount --sites` shares the parser, so one file serves both. **Chromosome naming is auto-converted**: UCSC (`chr22`), Ensembl (`22`) and NCBI RefSeq (`NC_000022.11`) spellings all resolve, via cghts's `CanonicalContig`/`ContigConverter`. Comparisons use canonical identity, and tabix lookups resolve against the index's own `RefNames()` — tabix matches names verbatim, so a bare `22` against a `chr22` index used to fail with `unknown reference`. Conversion preserves the source's own spelling in the store rather than rewriting it. A contig the file lacks is an absence (no rows plus a warning), independent of whether the file is indexed; an unresolvable `--region` is an error, since that names a contig the caller asserts exists. `-v/--verbose` reports the chosen backend, the store's conversion provenance, per-variant AC/AN/AF, the ALT-call and hom-ref row counts, and how many calls the quality gate actually excluded — including a warning when the gate could not act because the field is absent, and when `--min-dp` differs from the value the store's runs were built at. All verbose output goes to stderr so the tabular stream stays parseable. A `--variant` **span selects by record overlap**, so a region query returns a deletion or gVCF block that begins before it and reaches in; the extent is stored per row as `ref_end` and computed from `len(REF)`, `INFO/END`, `SVLEN` and `FORMAT/LEN`. A store converted before that column existed selects on position alone and reports `HasRefSpans() == false`, which is a different answer rather than a slower one. **Queries prune row groups rather than scanning the whole file** (`cghts/varstore/prune.go`): input is coordinate-sorted and written in stream order, so parquet's per-group min/max on `pos` are tight, and a locus lookup skips every group that cannot contain it — measured 3.05x on a two-chromosome 1KG store (479ms to 157ms). **There are now reproducible benchmarks** (`internal/cmd/vcfcmd/bench_test.go`) over a seeded generated corpus rather than uncommitted 1KG data -- `go test -bench BenchmarkQueryPanel|BenchmarkStoreVsVcf`, scaled by `CGKIT_BENCH_SAMPLES`/`SITES`/`ROWGROUP`. Two findings worth knowing: one bulk query is ~349x a per-locus loop at 1000 targets and stays *flat* (7ms to 19ms across a thousandfold target increase) where the loop is linear, which is the measurement the single-`Calls` API was argued for; and against a **tabix-indexed** VCF a single-locus lookup is only ~1.9x faster, not the ~40x an unindexed VCF suggests -- the unindexed figure measures a file nothing can seek in, and quoting it would flatter the store. The 18x at 100 loci is partly ours: `VcfStore` only seeks for a single locus or region, so a multi-locus query scans and the index goes unused. Note also that `--row-group-size` at its 250,000 default puts a modest corpus in ONE row group, where position statistics can never exclude it and every lookup scans everything. Filters are conservative in one direction: they may keep a group holding nothing, never skip one holding a match, and the per-row checks are unchanged, so pruning can only affect how much is read. Chromosome bounds are only used when a group holds exactly one chromosome, since the statistics are lexicographic while chromosome names are not ordered that way. Note `--sample` queries cannot be pruned this way: every sample appears in nearly every row group, so the sample_id bloom filter always says maybe — making those fast would need a sample-major sort, which conflicts with the (chrom,pos) sort. There is deliberately **no `--classify`, no `--min-gq` and no `--region`**. The four internal states (carrier / uncertain / non-carrier / not-assayed) remain library machinery in `varstore.Classify`, because reconstructing a `0/0` from a store requires them, but they are not a CLI vocabulary: the genotype in the output already says which case occurred, so there is no state column to interpret. `--min-gq` went because callable runs are built from depth alone — a store retains no GQ for a genotype it never wrote down, so it could not gate a reference call where a VCF would, and the backends disagreed about which samples were reference (a real bug, caught by `TestHomRefBackendsAgreeUnderTheGate`). The `gq` column is still emitted, so filter downstream. The backends must agree: verified identical on 3,202 1KG samples, including at the worst-covered site in BRCA1. For that equivalence the query `--min-dp` should match the conversion `--min-dp`, since the Parquet side baked that threshold into its callable regions. An incomplete store (missing sites/regions, or built with `--no-callable`) makes `--hom-ref` return `ErrNotClassifiable` rather than degrade — reporting an unobserved sample as reference would invent an observation. `--hom-ref` switches from "only the valid ALT calls" (the default) to "every interrogated site" (the `gt` column separates them): in `--variant` mode the samples that are 0/0 at the locus, in `--sample` mode the catalog sites that subject was 0/0 at. It is **stricter than the internal `non_carrier` state**, and the difference is the whole point: at a multiallelic record a 0/2 sample is not a carrier of allele 1, but it is not reference either, so it appears under neither — emitting `0/0` for it would be a genotype the source never contained. Both backends therefore key the exclusion on the source *record* (`Locus.Record()`, i.e. chrom+pos+ref), not the split locus, and the disqualifying ALT call is looked up ungated, since a below-gate ALT makes a sample an uncertain carrier rather than a reference observation. The same bounds apply as to any reference claim: the gate must admit the reference call (a 0/0 at DP 3 under `--min-dp 10` is not an observation worth making), an off-catalog locus yields nothing, and an incomplete store returns `ErrNotClassifiable` in both modes. One asymmetry is unavoidable and is the one place the backends do not agree byte-for-byte: a store keeps only ALT genotypes, so a reference call recovered from one is a synthesized `0/0` with no DP/AD/GQ and no recoverable ploidy or phasing, where the same query against a VCF reports the recorded genotype and its quality fields — *which* rows appear is identical, and `-v` says so. `--format list` is refused with `--hom-ref`, since bare sample ids cannot say which are carriers and which are reference. In `--sample` mode this walks the whole sites catalog — roughly one row per variant in the source — so `--region` is what keeps it bounded. `--format vcf` emits a genotype matrix — one record per site, one column per sample — through cghts's `VcfWriter`, so `-o NAME.vcf.gz` bgzips and `--tbi` indexes. It **implies `--hom-ref`**, because a matrix that cannot tell an observed `0/0` from an unobserved `./.` asserts far less than the data supports, and it therefore inherits the `ErrNotClassifiable` refusal. `INFO` carries `AC`/`AN`/`AF`/`NS`/`nhomalt` **recomputed over the samples in the file** rather than copied from the store, since over a subset the catalog's counts are for the wrong denominator; a header note records that `AN` is depth-gated and so can differ from the store's own ungated `AN`. Only one locus is buffered at a time, which the store-order guarantee makes possible. **Every non-VCF output shares one tabular layout** — `chrom pos ref alt sample gt dp min_dp ad_ref ad_alt gq` — so results concatenate, sort and cut the same way whichever selectors were named; `--sample` used to lead with the sample column. Rows stream rather than accumulate, and arrive in the **store's own order** — contig order as written, *not* lexicographic, since sorting `chrom` as a string puts `chr10` before `chr2` and yields an unindexable VCF. Within a locus they are ordered by sample. `min_dp` is the tightest lower bound on depth the backend can vouch for: the recorded depth where there is one, the conversion `--min-dp` for a reference call reconstructed from a store (the run it came from is the evidence the site was covered), `.` where nothing is known. Writing that threshold into `dp` instead would assert a depth the data never had, which is the same class of error as writing `0/0` for an unassayed sample.
